# Отчёт по инспекции технического долга проекта Quick Datings

## 1. Инспекция проекта (Выявление признаков ТД)

### 1.1 Непонятный / нечитабельный код
*   **Backend:** Код соответствует стандартам FastAPI и утилитам (black, isort). Названия переменных и функций осмысленные. Присутствует docstrings в основных модулях. *Вердикт: Незначительный долг* (можно улучшить документирование сложных бизнес-правил, если они появятся).
*   **Frontend:** React-компоненты используют TypeScript, типы прописаны. Стили вынесены в CSS-файлы. *Вердикт: Код читаем*.
*   **Проблема:** В репозитории отсутствует файл `.pre-commit-config.yaml` и явно не настроены линтеры (Flake8, ESLint) в CI. Это может привести к постепенному накоплению нечитаемого кода в будущем.

### 1.2 Дублирующийся код
*   **Backend:** В слое репозиториев (`base.py`, `user.py`) используется наследование, что исключает дублирование CRUD-операций. Модели Pydantic переиспользуются.
*   **Frontend:** На данный момент есть только две страницы (Login, SignUp). Визуально они похожи. Формы (инпуты, кнопки) не вынесены в отдельные переиспользуемые компоненты. Стили прописаны в каждом файле отдельно. *Вердикт: Средний долг*.

### 1.3 Отсутствие автоматизации
*   **Сборка и развёртывание:** Автоматизация присутствует (docker-compose up). Это плюс.
*   **Тесты:** В проекте **полностью отсутствуют тесты** (юнит-тесты, интеграционные тесты). Нет папки `tests/`, нет зависимостей типа `pytest` в `requirements.txt`.
    *   *Это критический технический долг.* Без тестов рефакторинг опасен, а добавление нового функционала может сломать существующий (регрессия).

### 1.4 Запутанная архитектура и ненужные сложные зависимости
*   Архитектура чистая (разделение на `api`, `services`, `repositories`, `models`). Зависимости явно прописаны в `requirements.txt`. *Вердикт: Долга нет*.

### 1.5 Медленные / неэффективные средства
*   На данном этапе развития проекта проблема не наблюдается. *Вердикт: Долга нет*.

### 1.6 Незакоммиченный код / долгоживущие ветки
*   Репозиторий содержит все ключевые файлы (.gitignore настроен). Информации о долгоживущих ветках нет (предполагаем, что работа ведется в main/master или короткоживущих ветках). *Вердикт: Долга нет*.

### 1.7 Отсутствие / несоответствие технической документации
*   **API:** Документация генерируется автоматически через Swagger (FastAPI) и доступна по `/docs`. Это отличный стандарт.
*   **Архитектура:** Отсутствует описание архитектуры проекта, структуры БД (миграции), процесса разработки и деплоя в `README.md`. *Вердикт: Средний долг* (усложняет онбординг новых разработчиков).

### 1.8 Отсутствие тестовой среды
*   Среда для разработки есть (локальный Docker). Отдельной выделенной тестовой среды (staging) для заказчика/тестировщиков нет. *Вердикт: Незначительный долг* (актуален при выходе на production).

### 1.9 Длинные циклы интеграции / отсутствие непрерывной интеграции (CI)
*   В репозитории нет конфигурации CI (например, `.github/workflows/*.yml` для GitHub Actions). Нет автоматического запуска линтеров и тестов при пуше. *Вердикт: Средний долг*.

## 2. План мероприятий по устранению технического долга

План составлен в порядке приоритетности (от критического к желательному).

| № | Категория долга | Мероприятие | Ожидаемый результат |
| :--- | :--- | :--- | :--- |
| **1** | **Отсутствие тестов** | Написать интеграционные тесты для API (SignUp, Login) с использованием `pytest` и `TestClient` FastAPI. Добавить тесты для репозиториев и сервисов (мокая БД или используя тестовую in-memory БД). | Гарантия работоспособности ядра приложения. Возможность безопасного рефакторинга. |
| **2** | **Отсутствие CI** | Настроить GitHub Actions (или GitLab CI). Добавить шаги: линтинг (ruff, flake8), проверка типов (mypy), запуск тестов. | Автоматическая проверка качества кода при каждом коммите. Предотвращение поломок. |
| **3** | **Дублирование во Frontend** | Вынести общие элементы UI (поля ввода, кнопки, карточки) в отдельные компоненты (UI-kit) внутри папки `src/components/ui`. Переписать стили с использованием CSS-модулей или CSS-in-JS для переиспользования. | Уменьшение кода, упрощение поддержки и изменения дизайна в будущем. |
| **4** | **Отсутствие документации** | Дополнить `README.md`: схемой архитектуры, описанием процесса добавления миграций БД (Alembic), инструкцией по запуску тестов и линтеров. | Ускорение онбординга. Прозрачность проекта. |
| **5** | **Линтеры** | Добавить конфигурационные файлы для линтеров (`.flake8`, `pyproject.toml` для black/isort, `.eslintrc.js`) и интегрировать их с pre-commit хуками. | Стандартизация кода, исключение человеческого фактора при форматировании. |
| **6** | **Тестовая среда (Staging)** | Создать отдельный docker-compose профиль для staging (или настроить деплой на бесплатный хостинг типа Render/Railway для тестовой ветки). | Возможность демонстрации заказчику и финального тестирования перед выкаткой в прод. |

## 4. Сравнение объёма долга и недоимплементированных фич

*   **Текущий объём долга:** Значительный. Ключевая проблема — **отсутствие тестов**, что делает уязвимым весь текущий и будущий функционал. Остальной долг (дублирование стилей, отсутствие CI) замедляет разработку, но не останавливает её.
*   **Недоимплементированные фичи:** Исходя из названия (Quick Datings — аналог Tinder), скорее всего, в ближайших планах: функционал "лайков", создание профиля с фото, свайпы, чаты.
*   **Риск:** Начинать разработку сложных фич (например, WebSocket для чатов) на проекте без тестов и CI — значит **сознательно накапливать ещё больший долг и рисковать стабильностью**. Любое изменение моделей БД или логики авторизации может сломать существующий вход/регистрацию, и это обнаружится только при ручной проверке.

## 5. Выводы и коррективы в план разработки

**Вывод:** Устранение технического долга необходимо в **частичном, но критическом объёме**. Нельзя начинать реализацию нового функционала, пока проект не будет покрыт базовыми тестами и CI.

**Обоснование:**
Без тестов (п.1) и автоматической проверки (п.2) проект находится в зоне высокого риска. Текущий скелет (авторизация) — это фундамент. Если фундамент сломается при добавлении "лайков" или "чатов", починить его будет сложнее, чем написать тесты сейчас.

Дублирование кода во фронтенде (п.3) можно устранять параллельно с разработкой новых страниц (например, сразу создавать UI-компоненты при верстке страницы профиля). Выделять отдельное время на рефакторинг двух похожих форм (Login/SignUp) можно, но менее приоритетно, чем тесты.

### Корректировка плана разработки (Рекомендация)

Вместо того чтобы бросаться писать "фичу лайков", предлагается следующий **спринт 0 (Технический)**:

1.  **Неделя 1 (Приоритет: Стабильность):**
    *   **Мероприятие 1:** Покрытие тестами auth-функционала (SignUp, Login).
    *   **Мероприятие 2:** Настройка CI (GitHub Actions) для автоматического прогона этих тестов.
    *   **Мероприятие 5:** Настройка линтеров и pre-commit хуков.

2.  **Неделя 2 (Параллельно с новой фичей):**
    *   **Новая фича (например, "Редактирование профиля"):** Разработка новой фичи.
    *   **Мероприятие 3 (Рефакторинг UI):** В процессе создания новых форм для профиля, разработчик сразу выносит общие инпуты и кнопки в отдельную библиотеку компонентов. Это не отдельная задача, а стандарт разработки.
    *   **Мероприятие 4 (Документация):** В конце спринта, перед сдачей фичи, обновить README, описав, как работать с новыми компонентами и тестами.

3.  **По мере необходимости (Бэклог):**
    *   **Мероприятие 6 (Staging):** Настроить перед первым релизом в Production или перед началом пользовательского тестирования.
